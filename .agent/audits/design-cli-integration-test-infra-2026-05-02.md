5. **NKey seed format for real NATS connection not specified** — The ADR states "TestMain generates a real NKey user keypair (`nkeys.CreateUser`). Test `auth.json` contains the real seed." But `connectNATS` (import.go:366-382) calls `nats.UserJWT(...)`, which requires both a JWT and an NKey seed. The NATS server in plain mode (no operator JWT config) will reject JWT-authenticated connections unless it is also configured to accept them (e.g. with `--auth` or `--user`/`--pass`, or by running with no auth). The ADR does not specify how to configure the test NATS server to accept connections signed with a locally-generated NKey seed without a full operator/account/user JWT hierarchy. "NATS server runs in plain mode (no operator JWT config)" conflicts with `connectNATS` always using `nats.UserJWT(...)`.
   - **Doc**: "TestMain generates a real NKey user keypair (`nkeys.CreateUser`). Test `auth.json` contains the real seed. NATS server runs in plain mode (no operator JWT config), same as CP integration tests. Exercises credential loading and NATS connection code with real key material without requiring the full NATS operator/account JWT hierarchy."
   - **Code**: `connectNATS` (import.go:366-382) unconditionally calls `nats.Connect(natsURL, nats.UserJWT(...))`. A plain NATS server that receives a UserJWT connection will either accept it (if auth is disabled) or reject it (if any auth is configured). The CP integration tests use plain NATS but do not call `connectNATS` — they use the raw `nats.Connect` without JWT auth. The ADR does not show how to make the JWT path pass against a no-auth NATS server, or whether a different connection path is used.

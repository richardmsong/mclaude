1. **`CLIDeviceCodeRequest.PublicKey` not decoded or stored in code** — The ADR says "add `PublicKey string` to `CLIDeviceCodeRequest`; store the public key in the device-code record; use it in verify handler for JWT issuance." The current code at `mclaude-control-plane/device_auth.go:35` shows `type CLIDeviceCodeRequest struct{}` — empty. `cliDeviceCodeEntry` (line 15-22) has no `PublicKey` field either. `handleCLIDeviceCodeCreate` (line 91) decodes nothing from the request body. `handleCLIDeviceCodeVerify` (line 245-252) falls back to `user.NKeyPublic` from the DB, which is NULL for freshly admin-created test users, then calls `IssueUserJWTLegacy` without any client NKey. The ADR describes three concrete changes: (a) add `PublicKey string` to `CLIDeviceCodeRequest`, (b) add `PublicKey string` to `cliDeviceCodeEntry`, (c) decode it in `handleCLIDeviceCodeCreate` and (d) use it in `handleCLIDeviceCodeVerify` instead of `user.NKeyPublic`. All four sub-changes are absent from the code. A developer implementing this knows what fields to add and where, but the ADR does not specify: how should the verify handler reconcile the stored `PublicKey` with the freshly-generated NKey seed the CLI writes to `auth.json`? The CLI's `RunLogin` generates an NKey pair locally, sends `publicKey` in the device-code request, and later writes both `jwt` and `nkeySeed` to `auth.json`. The JWT must be issued with that same public key so the seed signs NATS nonces. The ADR says "use the stored `publicKey` from the device-code record" but does not say what happens when `PublicKey` is empty (e.g., a user who navigates to the verify URL manually without going through the CLI). Does the verify handler reject the request, fall through to `user.NKeyPublic`, or issue a legacy JWT? This fallback path must be specified to implement without guessing.
   - **Doc**: "add `PublicKey string \`json:"publicKey"\`` field and decode it in `handleCLIDeviceCodeCreate`; store the public key in the device-code record. In `handleCLIDeviceCodeVerify`, issue the JWT using the stored `publicKey` from the device-code record (not `user.NKeyPublic`, which is NULL for freshly admin-created test users)."
   - **Code**: `device_auth.go:35` — `CLIDeviceCodeRequest struct{}` (empty); `cliDeviceCodeEntry` has no `PublicKey` field; verify handler uses `user.NKeyPublic` only.

2. **Admin API does not issue NATS credentials; "TestMain requests credentials via admin API" is unimplemented** — The ADR states "TestMain requests credentials via admin API after user creation. Stores as `cli-integration/.test-creds.json`." and the NATS decisions row says "Admin API issues NATS JWT + NKey seed for the test user." The actual admin API (`mclaude-control-plane/admin.go`) provides `POST /admin/users` (returns `{id, email, name}` — no credentials), and no other endpoint issues NATS JWT+seed to an arbitrary user. `POST /auth/login` (not admin) issues JWT+seed, but requires email+password over the public API port, not the admin port. There is no `POST /admin/users/{id}/credentials` or similar endpoint. A developer cannot implement TestMain credential acquisition without knowing: (a) does a new admin endpoint need to be added to CP to issue NATS credentials for an arbitrary user-ID? (b) or should TestMain use `POST /auth/login` on the public API port with the test user's password? (c) or should TestMain perform its own NKey generation + device-code flow? The ADR is silent on which approach to take and what CP changes are required.
   - **Doc**: "TestMain requests credentials via admin API after user creation." / "Admin API issues NATS JWT + NKey seed for the test user."
   - **Code**: `admin.go:38-43` — `AdminUserResponse` has only `{ID, Email, Name}`; no admin endpoint issues NATS credentials.

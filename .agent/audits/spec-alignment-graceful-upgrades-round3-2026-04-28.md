### Non-clean findings

**GAP [SPEC→FIX]** (#23): "`jsToNatsMsg` adapter wraps JetStream `jetstream.Msg` as `*nats.Msg` for existing handlers" → spec-session-agent.md §NATS JetStream Streams should note the interface adaptation required between the JetStream fetch loop and the existing handler functions (which accept `*nats.Msg`).

**GAP [SPEC→FIX]** (#31): "Reconciler watches `session-agent-template` ConfigMap and re-enqueues all MCProject CRs when the image changes" → spec-state-schema.md §ConfigMap: `{release}-session-agent-template` currently says "Readers: reconciler (reads on startup to template Deployments)". Must be updated to document that the reconciler also watches this ConfigMap and triggers re-reconciliation of all MCProject CRs on change — this is the mechanism that initiates pod rolling upgrades.

**GAP [SPEC→FIX]** (#38): "Session Detail Screen shows an 'Updating...' banner above the conversation when `state === 'updating'`; input box stays enabled" → spec-web.md §Session State describes Dashboard STATE_LABELS and StatusDot for the updating state, and mentions the input box remaining enabled, but does not mention the explicit banner visible in the Session Detail Screen. Must be added.

**PARTIAL [SPEC→FIX]** (#11): "`<status>killed</status>` is a child element of `<task-notification>`" → spec-session-agent.md §Graceful Shutdown step 6 renders this as `<task-notification status=killed>` (attribute style) while listing `<task-id>`, `<tool-use-id>`, `<output-file>`, `<summary>` as child elements — omitting `<status>` from the children list. ADR XML schema shows `<status>killed</status>` as a child element. The spec must list `<status>` as a child element to produce correct XML.

**PARTIAL [SPEC→FIX]** (#19): "`sanitizePath` 200-char boundary and wyhash/djb2 fallback" → spec-session-agent.md documents the path formula but not the 200-char threshold or hash function used for long paths. ADR notes the hash branch is "never reached in practice" but a divergent implementation would silently break path matching on restart for long CWDs. Recommend adding a brief note to the spec.

**PARTIAL [SPEC→FIX]** (#22): "JetStream fetch loop: batch size 10, FetchMaxWait 5s" → spec-session-agent.md describes durable pull consumers and routing but does not document the batch size (10) or fetch timeout (5s). These are operational parameters that affect latency and throughput; should appear in the spec.

**PARTIAL [SPEC→FIX]** (#24): "handleDelete and handleRestart publish `api_error` event on failure" → spec-session-agent.md §Error Handling table covers api_error publication for create failures only. Must add entries for delete and restart failure paths (both should publish `{type: 'api_error', request_id, operation: 'delete'|'restart', error}` to `events._api`).

**PARTIAL [SPEC→FIX]** (#43): "Message dropped after MaxDeliver=5 — indicates persistent handler bug" → spec-session-agent.md §Error Handling should include a row for this failure mode noting that the message is dropped and this indicates a handler is consistently failing.

**PARTIAL [SPEC→FIX]** (#44): "Pod crash mid-drain (after publishing some shell notifications)" → spec-session-agent.md §Error Handling covers the general pod-crash case. The mid-drain idempotency guarantee (already-published notifications are durable; unpublished in-flight shells are simply lost because new pod has empty map, no duplicate publish) is not documented as a distinct scenario.

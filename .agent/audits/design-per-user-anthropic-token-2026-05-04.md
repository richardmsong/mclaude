The ADR's Impact section lists "add `user_host_tokens` table … to `docs/spec-state-schema.md`" as a required spec update, but the ADR is only about the design decision — the state schema has not been updated. A developer reading only the state schema (which they must follow per its own header) sees no `user_host_tokens` table definition to implement against.
   - **Doc**: "docs/spec-state-schema.md: add `user_host_tokens` table … remove DEV_OAUTH_TOKEN"
   - **Code**: `docs/spec-state-schema.md` has no `user_host_tokens` entry, no `x25519_public_key` on `hosts`, no `user-anthropic-{uslug}` Secret, no `mclaude-host-key` Secret.

A developer cannot determine: whether it is request/reply or fire-and-forget, what the payload is, what authorization is required, or whether the host JWT already has permission to subscribe to it.

5. **Host JWT permission not verified to cover `token.updated`** — The controller subscribes to `mclaude.hosts.{hslug}.token.updated` to receive K from CP. The existing host JWT `Sub.Allow` in the state schema is `mclaude.hosts.{hslug}.>` which would cover this subject, but the ADR does not state this explicitly and does not update the JWT permissions section in the state schema. If the host JWT `Sub.Allow` is ever tightened, this subscription will silently break. The subject also needs a `Pub.Allow` on the CP side — the ADR does not specify which NATS identity CP uses to publish this subject.

7. **CLI `mclaude auth anthropic` key derivation contradicts the SPA flow** — The ADR describes two incompatible K derivation strategies in the same document. The SPA uses "fresh ephemeral K generated per token-set operation (not derived from seed)" per the Decisions table. A developer implementing the CLI does not know which strategy to use; the Decisions table explicitly rejects HKDF in favor of ephemeral K.
   - **Doc (Decisions table)**: "Symmetric key K | Fresh ephemeral K generated per token-set operation (not derived from seed) | Simpler; K_wrapped in DB is sufficient for recovery"

The ADR does not specify the namespace of `mclaude-host-key`, the cross-namespace access mechanism, or the RBAC needed for the session-agent pod's ServiceAccount to read it.
   - **Doc**: "Session-agent pod mounts: `/secrets/host-key/sym-key` — from `mclaude-host-key` (host-level Secret, read-only)"
   - **Code**: `mclaude-controller-k8s/reconciler.go` session-agent pod is in namespace `mclaude-{userSlug}`. The reconciler's RBAC Role (line 194) grants `get` on `user-secrets` only, with no reference to `mclaude-host-key` or cross-namespace access.

1. **`user-tokens-{uslug}` Secret is mounted by the user-agent Deployment before it exists** — The controller reconciler loop (step 7) creates the user-agent Deployment mounting `user-tokens-{uslug}` Secret at `/secrets/tokens/`. This Secret is not created by the controller — the controller only creates `user-agent-key`, `user-secrets`, and `user-config`. Neither the ADR's Component Changes section nor the spec-k8s-architecture.md reconciler loop specifies who creates an empty `user-tokens-{uslug}` Secret before the Deployment is applied. A developer implementing the controller or user-agent cannot resolve whether to: (a) create an empty `user-tokens-{uslug}` Secret in the controller's reconciler before applying the Deployment; (b) mark the volume mount as optional; or (c) have the user-agent create it via k8s API before the Deployment mount requires it (impossible — the pod can't start to do anything until the Secret exists).
   - **Doc**: "Host controller creates user namespace `mclaude-{uslug}` + deploys user-agent pod." (Phase 1, step 4); user-agent spec: "Ensure `user-agent` Deployment. 2. **`entrypoint.sh` changes are underspecified — the `--nats-creds` flag and legacy `oauth-token` read are not addressed** — The ADR specifies exactly one change to `entrypoint.sh`: add `export CLAUDE_CODE_OAUTH_TOKEN=$(cat /secrets/tokens/${TOKEN_PROVIDER})`. But the actual `entrypoint.sh` (line 28-29) also conditionally exports `CLAUDE_CODE_OAUTH_TOKEN` from `user-secrets/oauth-token` — which the ADR says to remove. More critically, line 73 passes `--nats-creds "/home/node/.user-secrets/nats-creds"` to the session-agent binary. In user-agent-created pods, the `user-secrets` Secret is still mounted at `/home/node/.user-secrets` (the controller still creates `user-secrets`), but `nats-creds` is never written to it — spec-state-schema.md line 645 explicitly states "The `nats-creds` Secret key is not written." The session-agent binary will receive a non-existent credentials file path; unless `--auth-url` is also added, it will attempt to connect to NATS with no credentials and fail. The ADR describes session-agents as self-bootstrapping via challenge-response (`mclaude.hosts.{hslug}.api.agents.register` + HTTP challenge-response), which requires passing `--auth-url` (or `AUTH_URL` env var). The ADR does not specify: (a) removing line 28-29 (legacy `oauth-token` export), (b) removing the `--nats-creds` flag from the `exec session-agent` call, or (c) adding `--auth-url "${CONTROL_PLANE_URL}"` to the call.
   - **Doc**: "entrypoint.sh: reads token from mounted Secret: `export CLAUDE_CODE_OAUTH_TOKEN=$(cat /secrets/tokens/${TOKEN_PROVIDER})`" — only this one line is specified (Component Changes §mclaude-session-agent). "Session-agent JWT issuance: unchanged. Session-agent registers via `mclaude.hosts.{hslug}.api.agents.register` → CP issues JWT. Same path as today." (Project Provisioning Flow)
   - **Code**: `mclaude-session-agent/entrypoint.sh:28-29` — reads `oauth-token` from `user-secrets`; `entrypoint.sh:73` — `--nats-creds "/home/node/.user-secrets/nats-creds"`; `main.go:80,147,205` — `--nats-creds` is used to connect to NATS when `--auth-url` is not set. The session-agent's challenge-response path (via `agentAuth`) is only activated when `AUTH_URL != ""` (main.go:168).

3. **`GET /api/users/{uslug}/grants` response shape missing field: which grants trigger delivery** — The CLI spec (`mclaude auth anthropic` step 4) says "For each host in `GET /api/users/{uslug}/grants` with `status='accepted'`" it delivers the token. The CP spec says this endpoint returns `{hostSlug, status, createdAt, acceptedAt?, x25519Fingerprint?}`. The ADR says token delivery happens when "SPA decides to trust a host (trigger defined in ADR-0092)." ADR-0092 is not written yet. The CLI `mclaude auth anthropic --status` is supposed to print "per-host trust status" by reading this endpoint. A developer implementing the CLI cannot determine: (a) what `status` values indicate a host is ready to receive delivery (is `'accepted'` sufficient, or must `x25519Fingerprint` also be non-null?); (b) how the SPA knows when to auto-deliver on first token setup without ADR-0092. The CLI spec is specific enough to implement step 4 (accepted + pubkey endpoint), but the SPA trigger is explicitly deferred to an unwritten document, and the `--status` output (which per-host states to show) is underspecified.
   - **Doc**: "When SPA decides to trust a host (trigger defined in ADR-0092)" (Host trust section); "`--status` prints `Connected` or `Not set`… for each accepted host, prints whether the user-agent has registered an X25519 pubkey" (CLI spec §mclaude auth anthropic).    - **Code**: ADR-0092 does not exist; the SPA trigger for delivery has no specification. CLI step 4 iterates `status='accepted'` grants — implementable. SPA delivery trigger is blocked.

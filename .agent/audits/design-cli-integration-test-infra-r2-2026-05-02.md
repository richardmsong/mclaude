1. **Device-code verify endpoint: wrong method, auth mechanism, and body format** — The ADR says TestMain goroutine 2 completes the code by authenticating via `POST /auth/login {email, token}` to get a session cookie, then posting to `POST /api/auth/device-code/verify {userCode}` with that session cookie. The actual `handleCLIDeviceCodeVerify` implementation (device_auth.go:183) only accepts `GET` (serves an HTML page) and `POST` (processes an HTML form via `r.ParseForm()`), NOT JSON. The form fields are `user_code`, `email`, and `password` — not a JSON body `{userCode}`. There is no session-cookie auth path: the endpoint directly authenticates via email+password form fields. A developer implementing the TestMain goroutine following the ADR's description would produce code that 404s or 400s at runtime.
   - **Doc**: "Authenticate as test user (POST `/auth/login {email, token}` → session cookie), then POSTs to `/api/auth/device-code/verify` with `{userCode}` and session cookie to mark code as verified."
   - **Code**: `device_auth.go:178,207-260` — `handleCLIDeviceCodeVerify` is a form-POST endpoint accepting `user_code`, `email`, `password` fields; it authenticates inline using the password fields and does not read a session cookie or a JSON body. The `/auth/login` pre-step described in the ADR is unnecessary and the JSON body format is wrong.

2. **Poll response: `pending` field vs. `status` field mismatch** — The ADR describes `RunLogin`'s poll detecting "completion" once the verify step fires, implying the poll wire protocol carries a boolean pending flag. The CLI code (`login.go:72`) decodes a `pending bool` field and handles HTTP 202 as pending. The actual CP poll response (`device_auth.go:53`) is `{status: "pending" | "authorized"}` — no boolean `pending` field. The CLI currently handles 202 as pending and 200 with non-empty `jwt` as success; the CP always returns 200 with `{status: "pending"}` for pending polls. This mismatch exists in production code, not just test code, but the integration test spec says a developer should wire `RunLogin`'s poll to detect the verify completion — a developer reading only the ADR cannot determine whether the poll protocol is the CLI's boolean-field contract or the CP's status-string contract, nor which side needs fixing.
   - **Doc**: "RunLogin's poll detects completion and writes auth.json."
   - **Code**: `login.go:226-228` treats HTTP 202 as pending; `device_auth.go:173-175` always returns HTTP 200 with `{status: "pending"}` — these are incompatible. The integration test will fail if the CP's 200+status-string response is never decoded as pending by the CLI, causing the poll to treat the first pending response as a success with empty `jwt` and time out.

A developer cannot implement this without choosing one of two paths and then making additional decisions.
   - **Doc**: "polls `GET /api/projects/{pslug}` (or KV) until `importRef` is cleared — meaning the session-agent completed unpack. Then asserts sessions visible via the sessions API. Timeout: 60s."
